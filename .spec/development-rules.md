# 开发规则

## 分支与范围

- 只在 `develop` 分支修改 Phantom。用户负责把特定版本冻结到 `main`。
- 根 `README.md` 预留给最终用户说明；架构和内部规则写入 `.spec/`。
- 不得把 `/wow-ui-source`、`/PhantomProject`、`/Shigure` 或 `/midnight` 纳入 Phantom 仓库。
- 四个外部源码目录作为只读参考。除非用户明确要求更新，不得修改、提交、切换分支、fetch、pull 或 reset。

## 代码表达

- 代码应优先清楚表达业务步骤；只有技术细节遮蔽业务流程、具有独立职责或确有复用边界时才抽取。
- 变量、函数、类、模块等代码标识符使用英文，并遵循对应语言与项目的既有命名方式。
- 业务解释和业务注释使用中文；API、字段、类型和协议名称保持其原始英文。
- 不为业余桌面工具擅自加入生产服务器式可用性、故障隔离或自动恢复机制。
- 不得以“运行时可以修”为理由交付已知的确定性失败。

## Python Type Hint

所有手写 Python 文件强制使用 Type Hint：

- 所有函数和方法参数、返回值。
- 类属性和实例属性。
- 容器类型。
- 类型不明显的局部变量。

明显的简单局部变量与循环变量不强制逐个标注。第三方代码和生成代码不受本条约束。未来应配置静态类型检查并把手写源码纳入检查范围。

## 必要文档头

新建的业务实现文件，或本次任务中发生实质修改的业务实现文件，需要完整文件头。局部修改遵循已有风格，不为补模板扩大改动。第三方库、测试、脚本、配置、工具、生成代码、锁文件和纯数据文件不要求该头部。

Lua 文件遵循下节的专用格式；其他文件没有既有格式时，使用语言原生注释语法并保留以下英文标签：

```text
Summary:
    一行说明文件主要用途，不超过 120 个字符。
Description:
    说明业务内容结构或单一业务流程。
Key Variables:
    每行记录一个重要业务变量及含义；没有时写 None。
Change Log:
    YYYY-MM-DD: Added/Changed/Removed/Improved 已知的具体变更
```

不得编造历史。复杂函数内部只在有助于理解业务流程时增加解释，不以注释数量作为质量指标。条件插件还要满足 [plugin-system.md](plugin-system.md) 的专用契约说明。

## Lua 文件结构与注释

手写 Lua 文件按以下顺序组织，沿用 `phantom/lua/runtime/` 的分区标记；没有声明的分区也保留标记：

1. 文件头：使用 Lua 长注释，必须包含 `original`、`uuid`、`摘要`、`描述`、`修改记录`。
   - `original` 记录相对 `phantom/lua/` 的源码路径，沿用 `runtime\01_addon.lua` 格式，供未来发布改名定位源文件。
   - `uuid` 是供未来发布改名使用的唯一标识；已有 UUID 唯一时保留，不因补注释重新生成。
   - `摘要` 简要说明文件用途；`描述` 详细说明本文件承担的功能和业务流程。
   - 保留已有的 `runtime_index` 等元数据与历史记录，不编造历史。
   - `修改记录` 仅在新增或修改业务逻辑时增加；修复 bug、增减注释不增加记录。
2. `namespace initialization`：固定只有 `local addonName, addonTable = ...`。
3. `api cache`：集中本地化文件中使用的 WoW 官方 API 与 Lua API，每项声明使用中文行尾注释说明用途。官方全局对象、枚举引用也在此集中声明；通过对象调用的方法保留原有调用方式。
4. `variable reference`：集中声明插件内部的跨文件本地引用，每项使用中文行尾注释说明用途。引用必须保留原有初始化时机；运行期变化的状态不能缓存成加载期快照，仍通过共享表读取或写入。
5. `logical code`：按业务流程组织代码，为有业务含义的变量、步骤和分支补充必要的中文行尾注释；`end` 等结构行不强制加注释。

补全注释和 API 本地化必须保持业务行为、调用顺序与状态更新方式不变，不借此重构或修复其他逻辑。描述以当前实现和已核验事实为准，不把预期行为写成已实现的保证。

## WoW API 与事实核验

开发前从 [`.context/README.md`](../.context/README.md) 进入相关主题。技术事实按以下顺序取证：

1. 当前目标版本的 `/wow-ui-source`。
2. Blizzard 随源码提供的变更信息和 API 定义。
3. `/PhantomProject`、`/Shigure` 与 `/midnight` 中经验证的历史实现。
4. 其他资料仅作为线索，必须回到版本源码核实。

面向 WoW 12.1 系列的易变结论必须记录核验日期和源码 revision。无法确认时标记“待验证”，不得提升为强制规则。处理 Aura、Secret Values、安全模板、受保护调用和战斗限制时，必须阅读对应 `.context` 专题。

## 安全与变更边界

- 不绕过 WoW 的保护机制或把 Secret Value 强制转换成普通值。
- 用户确认的运行期键位覆盖风险只适用于 `bind_key: true` 的既定行为，不扩大为其他不可逆操作授权。
- 配置结构、像素布局或插件公共契约的变化必须先更新相应规范和迁移决策。
- `.context` 是英文事实资料，`.spec` 是中文规范；不要把历史示例直接复制为规范。
